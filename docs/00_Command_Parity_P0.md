# Контракт команд и порядок P0

Эталон сравнения: справка официальных Android SDK Platform-Tools 37.0.1
(24.09.2026) и код предоставленного NekoFlash 6.0.0-alpha11. Команды desktop
клиента бывают операциями хоста, wire-сервисами и составными планами. Парсер
не выдаёт операцию одного вида за другой. `raw` адресован только wire-уровню;
он не выполняет host-алгоритмы desktop-клиента.

**Состояние реализации на этой ревизии:** есть типизированный разбор и
первый JVM-модуль ответов Fastboot wire и тестируемая классификация USB-интерфейсов.
По нажатию кнопки APK открывает
Fastboot USB-интерфейс, запрашивает `getvar:version` либо `getvar:product`
и закрывает сессию. На реальном устройстве подтверждены ответы `FAIL` на запрос
версии и `OKAY vayu` на запрос продукта. Дополнительно есть диагностический
ADB `CNXN` с классификацией первого ответа и автоматическая авторизация
ключом после выдачи USB-доступа, с ручным повтором. Каждая сессия закрывается
без запуска сервисов. Команды из таблицы и
терминал пока не имеют полного общего исполнителя. Для `getvar version`,
`getvar product` и `adb shell getprop ro.product.device` реализованы планы с
Preview и исполнители с FakeTransport-тестами. Панель ввода запускает только
эти три плана по кнопке; `getvar all`, `raw`, host-команды и параметры без
реализации отклоняются до обращения к USB. Два контроллера используют общий
исключительный захват USB-сессии. Успешный CI не переводит другие строки в
статус «готово». Следующая задача — расширить план и исполнение,
сохраняя явный отказ для остальных сценариев.

## Правила

1. Пользователь выбирает раздел, слот, файл и команду. Инвентарь устройства
   помогает показать факты и подсказки, но не служит списком разрешённых целей.
2. Параметр либо действует, либо команда завершается явной ошибкой до отправки.
   Игнорирование `-S`, `--force`, `--set-active` и иных опций запрещено.
3. Команда с известным desktop-смыслом создаёт типизированное намерение;
   неизвестная стандартная host-команда получает статус `Unsupported`.
   Неизвестный глагол Fastboot доступен как vendor wire-команда; явный `raw`
   сохраняет исходную строку без нормализации. Неизвестный глагол ADB не
   превращается автоматически в удалённую команду shell.
4. Ошибки устройства, отсутствующие возможности устройства и нарушения формата
   данных отображаются отдельно от локальных ошибок разбора. Время ожидания
   ответа пользователя на устройстве не обрывается общим дедлайном приложения.
5. Превью собирается из того же плана, который исполняется. Исполнитель не
   возвращает успех для ещё не реализованного типа шага.

## Объём P0: точный смысл ранее распознаваемых команд

| Семейство | Обязательный результат исполнения |
| --- | --- |
| `fastboot format[:TYPE[:SIZE]] PARTITION` | Узнать параметры раздела, создать подходящую ФС и прошить образ; не отправлять `format:PARTITION`. |
| `fastboot -w [COMMAND]` | Полный host-сценарий wipe, включая применимые `userdata`, `cache`, `metadata` и форматирование; сочетание с COMMAND сохраняется. |
| `fastboot wipe-super [SUPER_EMPTY]` | Прочесть метаданные образа, сформировать и прошить пустой super; не отправлять текст `wipe-super` как wire-команду. |
| `--set-active`, `--slot`, `-S`, `--force`, `--skip-*`, vbmeta-флаги | Учесть в плане в совместимых командах; каждая несовместимость явно диагностируется до исполнения. |
| `fastboot flash`, `flash vendor_boot:RAMDISK`, `boot`, `flash:raw`, `update`, `flashall` | Подготовить образы и план на стороне хоста, учесть слоты, fastbootd, sparse/resparse и `max-download-size`; `vendor_boot` требует fetch и перепаковки, `update` и `flashall` входят в P0. |
| `adb shell`, `logcat`, `exec` | Правильный сервис и режим, коды выхода, отмена и ограниченная память для долгого вывода. |
| `adb push`, `pull`, `sync` | Рекурсивность и опции CLI, Sync v2 при поддержке устройства с откатом на v1. |
| `adb install`, `install-multiple`, `sideload` | Точные host-сценарии, поддержка одного APK в `install-multiple`; терминал и UI используют один исполнитель. |
| `adb reboot`, `root`, `unroot`, `remount`, `usb`, `tcpip`, `uninstall` | Запуск нужных сервисов и корректное состояние сессии после ожидаемого отключения. |
| `adb raw`, `fastboot raw` | Передать wire-запрос без подмены команды и без списка разрешённых имён. |

Команды Platform-Tools, ещё не вошедшие в P0, остаются в таблице развития:
`adb pair/connect` и дальнейшая сетевая работа, `forward/reverse`,
`install-multi-package`, `bugreport`, прочие host-сервисы. У каждого будет
отдельный тип намерения и тесты; текущий парсер сообщает `Unsupported`, когда
хостовая реализация отсутствует. В P0 `adb tcpip` выводит понятное предупреждение
о потере USB-соединения. Доступ к raw-сервису остаётся возможен.

## Порядок работы

1. **Точный смысл.** Типизированный разбор → план → host-операция → wire-ответ;
   ни одного распознаваемого глагола с ложным результатом. Проверки на `format`,
   `-w`, `wipe-super`, `--set-active`, `-S`, `sideload`, `uninstall`, `raw`.
2. **Данные.** Для Fastboot `download` отдельно реализована ограниченная потоковая
   DATA-фаза с проверкой объявленной длины и обрывов в FakeTransport. Перед
   командой `flash` ядро уже проверяет `max-download-size` и успешный ответ на
   `download`, но этот исполнитель ещё не связан с выбором файла и UI Preview.
   ADB учитывает согласованный `maxData` для фиксированного чтения с лимитом
   памяти. Далее нужны Sync v2/64 бит, ограничение памяти долгого вывода,
   Fastboot resparse и файлы больше 4 ГиБ с FakeTransport и обрывами.
3. **Новые команды.** Добавлять host-команды из матрицы с тестами смысла,
   не выдавая неизвестные глаголы за удалённый shell или bootloader wire.

## Владение транспортом

Одна сессия владеет физическим USB-соединением. У ADB один читатель пакетов,
сериализованный писатель и несколько отдельных stream-id: `logcat` не блокирует
другой ADB-поток. Fastboot DATA и переход режима получают исключительный доступ.
Ожидание user-операции не разрывается по фиксированным 15/30/120/600 секундам.
После неясной очистки native-транспорта сессия не используется до доказанной
очистки или пересоздания. Новый транспорт получает новое CNXN.

## Проверка готовности

Парсерные тесты доказывают только разбор. Для заявления о готовности P0 нужны
тесты построенного плана, протокольные транскрипты и испытания с реальными
образами разных размеров. Текущие аппаратные проверки выполняются только на
одном POCO X3 Pro с разблокированным загрузчиком; совместимость с другими
конфигурациями по этим результатам не заявляется. Статический анализ legacy и
запуск справки Platform-Tools не заменяют аппаратные проверки.

Сверка протокола: [официальный выпуск Platform-Tools](https://developer.android.com/tools/releases/platform-tools),
[описание Fastboot wire](https://android.googlesource.com/platform/system/core/+/refs/heads/main/fastboot/README.md)
и [описание ADB](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/dev/protocol.md).
