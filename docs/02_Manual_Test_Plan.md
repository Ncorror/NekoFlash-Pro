# Сборка, отчёты и план проверок

Это инструкция для **нынешнего** `Ncorror/NekoFlash-Pro`. Тесты из архивного `NekoFlash-main.zip` принадлежат другой реализации и в здешнем Actions не запускаются.

## Сборка и результаты GitHub Actions

- Текущая конфигурация: JDK 17, Gradle Wrapper `9.5.0`, AGP `9.2.1`, Kotlin/Compose compiler `2.4.20`, `compileSdk` и `targetSdk` 36. В рефакторинге архива AGP `9.3.2`, Kotlin `2.4.10`, `compileSdk` 37; обновление версий потребует отдельного CI-прогона.
- Workflow `.github/workflows/android-ci.yml` запускается при push/PR в `main` и вручную. Проверяет пять JVM-модулей, Android lint и `:app:assembleDebug`.
- APK находится в артефакте `NekoFlash-Pro-prototype-debug-<run number>`. Артефакт `NekoFlash-Pro-test-results-<run number>` содержит `build/verification/test-summary.md`, JUnit XML, HTML-отчёты, lint и **этот план**. Доступ: репозиторий → Actions → Pro prototype build → выбранный запуск → Artifacts. Отсутствие ошибок CI не подтверждает запись в целевое устройство.

Для локальной машины с JDK 17 и Android SDK 36:

```sh
bash ./gradlew :engine:test :core:transport:test :core:fastboot:test :core:adb:test :core:diagnostics:test :app:lintDebug :app:assembleDebug --no-daemon
```

## Termux и обновления репозитория

Termux используется как Git-клиент; APK собирается в Actions. В авторизованном Termux:

```sh
pkg install git gh
gh auth status
gh auth setup-git
gh repo clone Ncorror/NekoFlash-Pro
cd NekoFlash-Pro
git status --short
```

Для своих правок `bash scripts/termux-push.sh "Краткое описание" README.md docs` проверит аккаунт и origin, получит изменения, покажет подготовленные файлы и запросит подтверждение в Termux. Скрипт не делает force push. Если GitHub уже обновился, сначала синхронизируйте клон. Не кладите ZIP диагностики, приватные ключи, прошивки и случайные выгрузки в коммит.

## Получение диагностики в установленном APK

1. Выполнить действие, после которого появился вопрос/сбой. Затем открыть раздел «Диагностика» и выбрать «Сохранить ZIP-отчёт». Android предложит место сохранения; Termux для экспорта не нужен.
2. Архив содержит `README.txt`, `environment.txt` (версия APK/Android/хост), `usb-descriptors.txt` (состояние доступа и интерфейсы), `events.log` (ограниченная история действий и результатов). Есть отдельная выгрузка событий в TXT. Системный `logcat` в ZIP сейчас не включён.
3. Перед передачей отчёта просмотреть его: сообщения об исключениях и коды устройств могут раскрывать дополнительные сведения. Сырые ключи ADB, подписи, токены и серийные номера не должны попадать в новый формат. Сам сборщик ZIP из архивного рефакторинга не выполняет автоматического обезличивания.
4. Записать рядом словами версию APK, действие и видимый итог. ZIP оставлять локально либо передавать отдельно; не вставлять его содержание в документацию/Issues без проверки.

## Ближайшая ручная проверка: один согласованный разблокированный target

| Шаг | Действие | Ожидаемое наблюдение |
| --- | --- | --- |
| 1 | Установить APK из успешного запуска Actions; отметить версию/подпись | APK запускается, тема тёмная, виден оранжевый акцент |
| 2 | Подключить целевое устройство в режиме Android с ADB | Интерфейс найден; Android запрашивает USB-доступ при необходимости |
| 3 | Разрешить USB; если целевое устройство просит разрешить отладку, подтвердить на нём | ADB получает `CNXN`, при повторном подключении используется прежний ключ, если APK обновлён с совместимой подписью |
| 4 | Запустить фиксированную ADB-диагностику; переподключить кабель | Ответ относится к новой сессии; предыдущий результат не приписывается новому подключению |
| 5 | Перевести целевой телефон в Fastboot; обновить список, выполнить только `getvar` | Видны отдельные ответы устройства; `FAIL` не описан как ошибка USB |
| 6 | Сохранить ZIP и проверить состав | Понятны состояние подключения, действие, peer-ответ и причина отказа без секретных данных; идентификатор поколения сессии ещё предстоит добавить |
| 7 | Отключить кабель во время read-only проверки | У приложения нет падения/самовольного повтора; устаревший результат не объявлен новым |

Проверка записи требует отдельно подтверждённых происхождения образа, раздела, точной версии APK, предпросмотра плана и ожидаемого исхода. Пока результат DATA/`flash` этой ветки на реальном устройстве не доказан, таблица выше не помечает прошивку успешной. Когда базовая передача будет проверена, отдельно замеряем размер и скорость файла на Java-пути и сравниваем будущий USBFS backend на одном и том же сценарии.
