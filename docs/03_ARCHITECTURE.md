# Архитектура

Как устроено приложение от USB до экрана. Правила корректности, на которые опирается каждый слой, — [02_INVARIANTS](02_INVARIANTS.md); порядок, в котором мы приходим к этой схеме, — [06_MIGRATION](06_MIGRATION.md) и [05_ROADMAP](05_ROADMAP.md).

## 1. Слои

```text
Интерфейс: рабочее место устройства, терминал, операции, диагностика
                 |
          Сценарии (use cases): подтверждения, предпроверки, планы команд
                 |
          Движок операций (владение, граница мутации, исход)
          /           |              \
        ADB        Fastboot        Recovery          Vendor (Mi Unlock)
         |            |               |                     |
         +------ Цель / Сессия (TargetId, SessionGeneration) +
                          |
                    USB-транспорт

Побочные системы: файлы (ArtifactSource/Sink) | диагностика | хранение
```

Главное правило: **протокольные движки моделируют протоколы, а не экраны.** Типизированные кнопки, сырая консоль, команды настольных `adb`/`fastboot`, план из нескольких команд и Mi Unlock вызывают один и тот же движок. Второго пути нет.

## 2. Цель и физическая сессия

- `TargetId` — логическая личность устройства с указанием источника: серийный номер переживает переподключение и смену режима, имя USB-подключения — нет.
- `SessionGeneration` — конкретное физическое подключение и захват. Каждое отключение/подключение/переперечисление создаёт новое поколение; старый handle непригоден навсегда.
- `TargetMode` — ADB, Recovery, Sideload, загрузчик Fastboot, fastbootd, неизвестно. Устанавливается протоколом, а не дескриптором.
- Состояния сессии: обнаружена → ждёт разрешения → готова ⇄ захвачена → закрыта (с причиной). Освобождение интерфейса возвращает сессию в «готова», не закрывая её.

Нельзя строить архитектуру вокруг одного изменяемого `currentDevice`/`currentConnection`.

## 3. Протокольные слои

- **USB** — обнаружение, классификация по дескрипторам, разрешение Android, захват/освобождение, bulk-ввод-вывод, тайм-ауты и отмена, владение поколением, метрики. USB не знает, что `flash:boot` «опасен» и что Mi Unlock — это Xiaomi. Нативный backend (USBFS) допускается для скорости, но его API остаётся транспортным.
- **ADB** — `CNXN`/`AUTH`, кадры, один физический читатель, сериализованный писатель, маршрутизатор потоков (`localId`/`remoteId`, ограниченный почтовый ящик на поток, `OPEN/OKAY/WRTE/CLSE`). Фундаментальная возможность — `openService(destination)`; поверх неё: shell v2 и откат, интерактивный shell, exec, sync, установка пакетов, reboot, сырой сервис, проброс портов, клиент Recovery-доказательств, специализированный транспорт Sideload. Учитываются согласованные возможности и `maxdata` устройства.
- **Терминал** разделяет неинтерактивную команду, интерактивный PTY, каналы `shell,v2`, откат, stdin/EOF/сигналы/клавиши, изменение размера. Эмулятор терминала — отдельный компонент интерфейса, а не часть протокола.
- **Fastboot** — синхронная модель транзакций хоста: запись команды, `INFO`, `TEXT`, `OKAY`, `FAIL`, DATA OUT, DATA IN, тайм-аут, обрыв, неоднозначная мутация. Один движок на всех потребителей, без списков разрешённых команд и без проверки lock state внутри.
- **Recovery** — определение режима, ограниченное чтение журналов через общий ADB, машина состояний Sideload, снимок до Sideload, передача, требование физического переподключения, корреляция и вердикт установки.
- **Vendor** (Mi Unlock) — оркестратор поверх публичных API цели, ADB/Fastboot, файлов и операций плюс отдельный сетевой клиент. Второй «XiaomiUsbManager» или второй Fastboot-движок запрещены.

## 4. Операции, файлы, диагностика

**Операция** — запись, которая переживает экран и процесс: `OperationId`, время, намерение, `TargetId`, `SessionGeneration` на старте, состояние своей машины, граница мутации, прогресс, файлы, исход, ответы устройства, ссылки на доказательства. У `FastbootFlash`, `AdbPull`, `Sideload`, `InstallApk`, `MiUnlock` свои машины состояний — общего глобального `Stage` нет. Долгую операцию держит движок уровня приложения и foreground-сервис типа `connectedDevice`, а не Activity/ViewModel. Запись хранится для истории и честного восстановления после смерти процесса, а не для «продолжить прошивку с середины»: после перезапуска — «завершена», «брошена до границы мутации, устройство не тронуто» или «требует проверки».

**Файлы**:

```text
ArtifactSource: имя, размер Long?, доступ SEEKABLE | NON_SEEKABLE | UNKNOWN,
                отпечаток при открытии и сейчас (размер, время, версия),
                последовательное чтение, произвольное чтение или null
ArtifactSink:   временное место, точный счёт, commit только после успеха,
                признак атомарной замены, abandon с причиной
```

Никакого образа целиком в `ByteArray`, никакой 32-битной арифметики байтов, `readBytes()` для образов запрещён. `content://` не считается перематываемым автоматически: если протоколу нужен произвольный доступ (Sideload), источник копируется во временный файл с прогрессом, хешем и проверкой места — решение принимается **до** передачи. SHA-256 считается потоком и не доказывает, что те же байты лежат на устройстве.

**Диагностика** — структурированные события каждого слоя (цель/сессия, USB, ADB-рукопожатие и потоки, транскрипт Fastboot, счёт байтов операций, корреляция Recovery, этапы vendor-сценария) и экспорт детерминированного архива. Диагностика не зависит от разбора строк интерфейса. Обезличивание — обязанность слоя, который собирает событие: ключи, подписи, токены, баннеры, серийные номера и произвольный вывод не пишутся.

## 5. Модули

### Целевая структура

Модуль заводится, когда у него есть настоящая граница владения и собственный контракт; пустых модулей «на будущее» нет.

| Модуль | Ответственность |
| --- | --- |
| `:app` | граф зависимостей, навигация, тема, Android-контроллеры до выноса в `feature:*` |
| `:core:model` | `TargetId`, `SessionGeneration`, `TargetMode` |
| `:core:diagnostics` | структурированные события, экспорт архива |
| `:core:operation` | запись операции, прогресс, граница мутации, восстановление после смерти процесса |
| `:core:artifact` | `ArtifactSource`/`Sink`, отпечатки, стажирование, SHA-256, запись с проверкой счёта |
| `:usb:api` | контракты USB без Android: дескрипторы, классификация, личность цели, сессии и поколения, политика разрешений, bulk-передача |
| `:usb:android` | Android USB Host: перечисление, приёмники подключения, запрос разрешения, захват, bulk-ввод-вывод |
| `:usb:native` | нативный backend USBFS для скорости Fastboot DATA (по результату измерения) |
| `:protocol:adb` | всё ADB, включая Sync, Sideload и Recovery-корреляцию |
| `:protocol:fastboot` | полоса, `getvar`, DATA OUT/IN, мутации, планы, lock state, разделы |
| `:engine` | разбор команд настольных `adb`/`fastboot` в типизированные намерения и план с Preview (имя модуля может смениться при переносе) |
| `:feature:*`, `:vendor:xiaomi` | выносятся из `:app`, когда появится второй потребитель или настоящая граница |

## 6. Направление зависимостей

| Модуль | Может зависеть от | Не может зависеть от |
| --- | --- | --- |
| `core:*` | друг от друга внутри `core:*` | `usb:*`, `protocol:*`, `feature:*`, `vendor:*`, `:app`, Android |
| `usb:api` | `core:*` | `usb:android`, `usb:native`, `protocol:*`, `feature:*` |
| `usb:android`, `usb:native` | `usb:api`, `core:*` | `protocol:*`, `feature:*`, `vendor:*` |
| `protocol:*` | `usb:api`, `core:*` | друг друга напрямую, `feature:*`, `vendor:*` |
| `:engine` | `core:*` | Android, `usb:*` |
| `vendor:*` | `protocol:*`, `core:*` | `feature:*` |
| `feature:*` | свои `protocol:*`/`vendor:*`, `core:*` | другой `feature:*` напрямую |
| `:app` | всё | протокольной и бизнес-логики в себе |

Модуль, чей публичный API раскрывает типы другого модуля, объявляет его как `api(...)`, а не `implementation(...)` ([ADR-0003](adr/0003_PHASE2_TECHNICAL_BASELINE_RU.md)). Границы `core:*` проверяются машинно (detekt), `:app` — ревью.

## 7. Стандарт кода

- **Одна ответственность.** Если класс не описывается одним предложением без «и» — делить. Больше ~300–400 строк или ~15–20 публичных членов — пауза на ревью; больше ~800 строк без ADR — блокирующее замечание.
- **Конкурентность:** `kotlinx.coroutines` + `Flow`, structured concurrency, scope привязан к `SessionGeneration`. Голых `Thread`/`Handler.postDelayed` в новом коде нет (текущие контроллеры репозитория на потоках уходят при переносе).
- **Ошибки:** ожидаемые исходы протокола — sealed-типы (`Успех/Ошибка/Отменено/Неизвестно` и их уточнения); исключения — только для ошибок программиста и невозможных состояний.
- **Иммутабельность:** `val`, `data class`, `sealed` по умолчанию; интерфейс получает неизменяемый снимок состояния и посылает действия. Никаких «god»-Activity/ViewModel.
- **Тесты — в том же коммите, что и код:** unit, симуляция протокола с фейковым транспортом (короткие чтения/записи, фрагментация, задержки, битые кадры, `INFO/TEXT/FAIL`, несовпадение длины DATA, обрыв на каждой интересной границе). Именование `<Subject>Test`.
- **Инструменты:** version catalog, detekt с проверкой границ модулей, проверки гигиены, локализации и Compose wiring — обязательные шаги CI ([07](07_BUILD_AND_TESTING.md#ci)).
- **Чистое дерево:** нет `.orig`/`.bak`, `Old/New/Temp`, закомментированных реализаций, заглушек в production, TODO без решения, параллельных путей.
- **Ревью спрашивает:** добавляет ли изменение искусственное ограничение? не спрятана ли политика в транспорт? сохраняется ли настоящий ответ устройства? определены ли владение, отмена и ошибки? нет ли второго пути? есть ли тесты отказов? нужен ли прогон на железе?
