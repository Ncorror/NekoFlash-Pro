# Архитектура и правила корректности

Это целевая схема, сопоставленная с классами предоставленного рефакторинга. [Фактически присутствующие модули](05_Source_Comparison.md) перечислены отдельно. Новую структуру вводим по слоям, сохраняя один production-путь.

## Границы

| Слой | Назначение | Рефакторинг в архиве |
| --- | --- | --- |
| UI и use cases | выбор цели, видимые подтверждения, состояние экранов | `:app` |
| Target/operation | идентичность устройства, поколение сессии, стадии, исход | `:core:model`, `:core:operation` |
| USB | классификация, запрос прав Android, claim/release, чтение/запись | `:usb:api`, `:usb:android` |
| Протокол | ADB services/stream router, Fastboot lane и точные ответы | `:protocol:adb`, `:protocol:fastboot` |
| Данные | streaming SAF-источник/приёмник, стадирование, digest | `:core:artifact` |
| Доказательства | события, bounded журнал, экспорт ZIP | `:core:diagnostics` |
| Будущие сценарии | Recovery, Mi Unlock и скоростной USB backend | выделять после реальной границы владения |

UI не содержит wire-протокол. USB не знает о `flash:boot` или Xiaomi. Протокольный слой не разрешает/запрещает команды по названию раздела. Mi Unlock и raw консоли используют тот же транспорт и движок, что и типизированный UI. Прототип сейчас организован иначе (`:engine`, `:core:transport`, `:core:adb`, `:core:fastboot`, `:core:diagnostics`, `:app`): названия архивных модулей нельзя считать уже созданными здесь.

## Сессия и автоподключение

Target — логическая цель, `SessionGeneration` — конкретное физическое подключение. Новое перечисление USB после отсоединения или смены режима создаёт новое поколение; старые ответы, разрешения на использование хэндла и непроверенное состояние загрузчика в него не переносятся. Классификация интерфейса по USB-дескриптору даёт ADB/Fastboot **вид интерфейса**, а режим Android/Recovery/fastbootd устанавливается протоколом.

Если интерфейс однозначно распознан, можно автоматически запросить системное разрешение USB и начать ADB-подключение; ADB-подтверждение ключа остаётся действием на целевом устройстве. Generic vendor bulk без достаточной уверенности требует ручного выбора, чтобы не занять чужое USB-устройство. При отказе/неоднозначности нет бесконечного повторного запроса. Выбор стратегии опирается на `UsbAutoConnectPolicy` архива и реальную модель USB Android.

## Протоколы и операции

- ADB: один physical reader, сериализованный writer, маршрутизатор по ID нескольких логических потоков, ограниченные очереди и контроль flow control. `shell,v2`, интерактивный shell, Sync и raw service — клиенты одного соединения.
- Fastboot: одна линия транзакций на USB-сессию; сохранить `INFO`/`TEXT`/`OKAY`/`FAIL`/`DATA` и точный счёт байтов. Никаких автоматических повторов после неоднозначной записи. Если peer уже мог изменить устройство, честный результат — `Unknown`.
- Recovery/Sideload: запросы блоков и успешная передача не равны успешной установке. Вердикт берётся из новых данных Recovery с привязкой к сеансу; отсутствие подтверждения оставляет `Unknown`.
- Операцией владеет приложение/служба, а не открытый экран. Для `flash`, `pull`, `sideload` и unlock нужны разные state machine и границы отмены. Успешный локальный хеш не доказывает запись на другом устройстве.

## Файлы, диагностика и скорость

Образы читаются потоком из Android SAF с `Long`-счётчиками. Доступ на произвольное чтение требуется доказывать или получить стадированием; весь ROM не загружается в память. Для Fastboot DATA OUT размеры и неизменность источника проверяются до/во время обмена; для DATA IN частичный результат не называется готовым файлом.

ZIP диагностики собирает ограниченные события, версии, сведения об интерфейсе, стадии передачи и ответы peer. Перед экспортом удаляются ключи, токены, серийные номера и произвольные команды/вывод, если они могут раскрывать данные. Архивный `DiagnosticBundle` упаковывает переданные ему секции и **сам по себе не обезличивает поля**: это обязанность собирающего слоя и обязательный пункт будущей проверки.

Приватный ключ ADB сейчас хранится в Android Keystore; будущие vendor-сессии тоже потребуют защищённого хранения. У текущего APK в манифесте стоит `allowBackup=false`; перед появлением новых приватных данных нужно отдельно проверить правила Android cloud backup и переноса на другое устройство. SAF-образы остаются пользовательскими файлами. Повторная debug-сборка должна иметь предсказуемую подпись: переустановка после удаления приложения уничтожает прежний приватный ключ и устройство запросит ADB-доверие снова. Настройку подписи не храним в исходниках.

Высокоскоростной Fastboot из legacy использует нативный USBFS/URB. В текущем прототипе и рефакторинге модуля `usb:native` нет. Переносить его можно только после измерений Java-пути и проверки cancel/drain/poison, исключительного владения интерфейсом и точного byte accounting; переключение backend посреди возможно мутирующей передачи недопустимо.
