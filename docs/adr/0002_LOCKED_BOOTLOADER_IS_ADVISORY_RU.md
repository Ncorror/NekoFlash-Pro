# ADR-0002 — Подтверждённый LOCKED bootloader — advisory, а не блокировка

> Решение перенесено из исторического среза без изменения смысла. Действующие правила проекта — [`docs/`](../README.md); бинарные архивы источников в текущем дереве не хранятся.

Статус: **ACCEPTED**
Дата: **2026-08-30**
Отменяет: D030 (Verified Bootloader Lock Protection)
Вводит: D031

## Контекст

`03_PROTOCOL_AND_SAFETY_INVARIANTS_RU.md` определяет четыре и только четыре класса оснований остановить операцию:

- **A. Hard invariant** — нарушена техническая достоверность; override недопустим.
- **B. Device authority** — устройство само отвечает отказом; показать реальный ответ, не подменять своей системой.
- **C. Advisory** — предупредить, дать продолжить, никогда не hidden deny.
- **D. User intent** — деструктивное намерение; точное подтверждение в guided UI, raw console остаётся доступной.

Verified Bootloader Lock Protection (D030) объявлялся «единственным специально принятым product-level исключением». Проверка показывает, что он не проходил ни один из четырёх классов:

- не A: рамка протокола цела, ownership на месте, `flash:<partition>` технически представим;
- не C и не D: это был hard block, а не предупреждение или подтверждение;
- фактически B: при `LOCKED` устройство отвечает `FAIL` само.

Но правило класса B гласит: *«показать реальный ответ/ограничение устройства. Не подменять его собственной authorization системой»*. Guard делал ровно подмену — упреждал ответ устройства решением хоста. Это тот самый паттерн, который `01_PRODUCT_CHARTER_RU.md` запрещает везде остальное.

## Решение

D030 отменяется. Product-level hard guards в NekoFlash отсутствуют полностью.

Намерение записать образ при подтверждённом `LOCKED` классифицируется как **D. User intent** и обрабатывается так же, как `erase userdata` и `format`:

- guided UI показывает предупреждение и требует **typed confirmation**: пользователь вводит `yes`;
- после подтверждения команда отправляется устройству без изменений;
- реальный ответ peer (`FAIL`, `OKAY`, `INFO`/`TEXT`) показывается без semantic подмены.

Предупреждение обязано честно называть ожидаемый исход: устройство почти наверняка отклонит запись ответом `FAIL` и раздел не будет изменён; на части загрузчиков сначала передаётся весь DATA-объём и только затем приходит отказ. Это экономит время оператора вместо того, чтобы его пугать.

### Границы

- `UNKNOWN`, unsupported query, противоречивый ответ и состояние из предыдущей generation **не равны** `LOCKED`: для них обычный advisory без typed confirmation. Иначе `UNKNOWN` де-факто снова приравнивается к `LOCKED`, что противоречит классу C.
- Raw Fastboot console выполняет `flash:<partition>` **без prompt**. Интерактивный ввод в сырой протокольной консоли ломает вставку и последовательность команд, а класс D прямо оставляет raw console доступной.
- Typed confirmation принадлежит **use-case/presentation** слою. `protocol:fastboot` не проверяет lock state как условие выполнения команды: иначе engine снова становится host-side gate, что запрещено `02_CORE_ARCHITECTURE_RU.md`. Это же гарантирует, что typed GUI и raw console используют один engine без разницы в правах.
- Mi Unlock и любой unlock workflow не затронуты.
- Успех unlock-команды не переводит состояние в `UNLOCKED`. После reboot/re-enumeration старая generation инвалидируется, состояние определяется заново.

## Рассмотренные альтернативы

**Оставить hard block.** Отклонено: он противоречит классу B и является единственным продуктовым запретом в проекте, чья заявленная позиция — отсутствие таких запретов.

**Предупреждение без typed confirmation (обычная кнопка).** Отклонено: запись образа при заблокированном загрузчике — намерение того же порядка, что `erase userdata`. Единая форма подтверждения для равных по разрушительности намерений понятнее, чем градация кнопок.

**Требовать ввод имени раздела вместо `yes`.** Более сильная защита от машинального подтверждения, но разная форма ввода для разных операций усложняет UI без пропорциональной пользы. `yes` выбран ради единообразия с `erase userdata` и `format`. Решение может быть пересмотрено, если практика покажет проблему.

**Typed confirmation и в raw console.** Отклонено: см. границы выше.

## Последствия

- Формулировка продуктового правила упрощается: исключений нет ни одного, остаются только четыре технических класса.
- Пользователь получает реальный ответ устройства вместо локального отказа — это точнее диагностически: `FAIL` может отличаться от ожидаемого и нести полезную информацию.
- В `protocol:fastboot` не появляется поле lock state как условие выполнения, что снимает риск обрастания engine «классификатором опасных команд».
- Требуется UI-компонент typed confirmation, общий для `erase userdata`, `format` и flash при `LOCKED`. Он реализуется в соответствующем UI-слайсе.
- Документы, ранее описывавшие guard, приведены в соответствие: `01`, `02`, `03`, `05`, `08`, `09`, `14`, `15`, `16`, `99`, `README.md`, `README.md`.
