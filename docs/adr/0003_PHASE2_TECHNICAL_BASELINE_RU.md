# ADR-0003 — Технический базис Phase 2

> Перенесено из архива `reference/archives/NekoFlash-main-2026-09-14.zip` без изменения текста решения. Ссылки вида «`07` §6.N», «`09`», «`16` §3», «`docs/…`» ведут в документы архива `NekoFlash-main/docs/`. Действующие правила проекта — [`docs/`](../README.md).

Статус: **ACCEPTED**
Дата: **2026-08-30**
Вводит: D032, D033

## Контекст

Phase 2 (USB + Target/Session) — первый слайс с реальным асинхронным вводом-выводом, владением ресурсами и временем жизни. Три решения до сих пор существовали неявно. Их надо зафиксировать до кода, а не после: в Legacy отсутствие такого решения дало цепочки `Handler.postDelayed` (`scheduleUsbPermissionTimeout`, `scheduleStartupUsbDiscovery`), а отсутствие анализатора размера/сложности позволило вырасти файлам на 2000–4000 строк никем не остановленными.

## Решение

### 1. Направление зависимостей выражается через `api`, а не `implementation`

Модуль, чей публичный API раскрывает типы другого модуля, объявляет эту зависимость как `api(...)`.

Текущее состояние нарушало это правило: `OperationContext.targetId: TargetId` и `DiagnosticEvent.targetId: TargetId?` — публичные члены, но `:core:model` объявлен как `implementation`. Проверено экспериментально: потребитель, видящий только `core:operation`, не компилируется — `cannot access class TargetId`. Сейчас это скрыто тем, что `:app` объявляет `:core:model` напрямую; `usb:api` и `protocol:*` из Phase 2 упрутся в это сразу.

Для получения семантики `api` в Kotlin JVM модулях применяется плагин `java-library`.

### 2. Конкурентная модель — `kotlinx.coroutines` + `Flow`

- structured concurrency; каждый запуск принадлежит явному scope;
- `CoroutineScope` привязан ко времени жизни `SessionGeneration`: detach/re-enumeration отменяет scope, старые задачи не переживают generation;
- никаких голых `Thread`, `Handler.postDelayed` и callback-цепочек в новом коде;
- наблюдаемое состояние — `Flow`/`StateFlow`, а не мутируемые поля с колбэками, как в Legacy `AdbProtocol`, державшем `onLog`/`onProgress` прямо в протокольном классе;
- ожидаемые протокольные исходы моделируются `OperationOutcome`/sealed-типами, исключения — только для программистских ошибок и невозможных состояний.

### 3. Dependency injection — ручной, пока это оправдано

DI-библиотека не вводится. На текущем масштабе явная сборка графа в `:app` читаема, не требует кодогенерации и не добавляет времени сборки в CI, который является единственной авторитетной средой сборки. Решение пересматривается отдельным ADR, когда ручной граф станет трудно поддерживать.

### 4. Статический анализ — обязательный CI-гейт

Вводится анализатор стиля и сложности Kotlin как обязательный шаг GitHub Actions, включая правила на размер файла/класса и на нежелательные импорты между модулями — чтобы направление зависимостей раздела 1 проверялось машиной, а не только на ревью. Из ktlint и detekt выбран detekt: ktlint покрывает форматирование, но не даёт ни правил сложности/размера, ни `ForbiddenImport`.

Пороги размера разделены на два уровня:

- **человеческий ориентир для ревью:** файл/класс свыше ~300–400 строк или ~15–20 публичных членов — пауза «точно ли это одна ответственность». Машина здесь не вмешивается;
- **машинный порог:** `LargeClass 600`, `LongMethod 60`, `TooManyFunctions 20` — отказ CI. Он намеренно ниже уровня, на котором размер становится проблемой, чтобы гейт ловил дрейф раньше, чем файл станет вторым `UsbSessionCoordinator`.

Превышение машинного порога возможно только осознанным изменением конфига с обоснованием в ADR, а не подавлением на месте.

Гейт внедрён отдельным changeset. Реализация:

- **detekt 1.23.8 как самостоятельный CLI-jar**, а не Gradle-плагин. Плагин связал бы гейт стиля с совместимостью AGP/Gradle/Kotlin: обновление toolchain могло бы уронить сборку продукта из-за анализатора. CLI от сборки независим. Версия и SHA-256 дистрибутива закреплены в `scripts/ci/check_kotlin_style.sh` так же, как закреплён Gradle Wrapper; несовпадение checksum — отказ.
- **Стиль и сложность.** `config/detekt/detekt.yml` — `LargeClass` 600, `LongMethod` 60, `TooManyFunctions` 20. `ReturnCount` оставлен на значении 2, но с `excludeGuardClauses`: ранний возврат из guard clause снижает вложенность, а не усложняет функцию; правило продолжает ловить настоящие многовыходные функции.
- **Границы модулей.** Отдельный конфиг `ForbiddenImport` на каждый защищаемый модуль: `config/detekt/core-boundaries.yml` для `core:*` и `config/detekt/usb-api-boundaries.yml` для `usb:api`. Так направление зависимостей из раздела 1 проверяется машиной, а не только на ревью. Новый модуль добавляется одной строкой в `scripts/ci/check_kotlin_style.sh`.
- **Compose учтён.** `FunctionNaming`, `LongParameterList` и `TooManyFunctions` игнорируют `@Composable`: PascalCase-имена и длинные списки параметров там нормальны, а без исключения гейт давал бы ложные срабатывания на каждом Composable.
- **Локально запускается той же командой.** Требуется Java; без неё проверка мягко пропускается с подсказкой, но в CI обязательна.

Проверено на реальном коде до внедрения: detekt 1.23.8 корректно разбирает Kotlin 2.4.10, текущее дерево проходит оба прогона, искусственные нарушения (`import android.content.Context` в `core:model`, функция на 70 строк) отклоняются с кодом возврата 1.

## Последствия

- `core:operation` и `core:diagnostics` получают `java-library` и `api(project(":core:model"))`; `usb:api` и `protocol:*` смогут зависеть только от нужного модуля.
- `kotlinx.coroutines` добавлен в version catalog вместе с первым настоящим использованием: `UsbSessionRegistry` публикует незавершённые сессии как `StateFlow`, а не отдаёт снимок по запросу. Объявлять зависимость раньше, чем она понадобилась, значило бы проверять её сборкой вхолостую.
- Отсутствие DI-библиотеки — осознанный выбор, а не упущение; его не нужно «исправлять» без нового решения.
- Статический анализ станет причиной отдельного красного CI при внедрении; это ожидаемо и лучше, чем обнаружить накопленный долг позже.
- Алиас плагина `android-library` в `build.gradle.kts` и version catalog объявлен `apply false` и пока не используется ни одним модулем. Это не заброшенный артефакт: он нужен модулю `usb:android` этой же фазы. Правило «модули не создаются пустыми» из ADR-0001 относится к Gradle-модулям, а не к объявлению плагина.
