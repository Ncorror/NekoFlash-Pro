# Как соединяем четыре источника

Сверены исходники текущего `NekoFlash-Pro`, загруженный `NekoFlash-main.zip` и два вложенных в него снимка `reference/archives/NekoFlash-main-legacy.zip` и `NekoFlash-A2-frozen.zip`. Контрольные суммы вложенных архивов совпадают с `reference/SHA256SUMS`. Вложенный legacy целый; именно он используется как эталон старого продукта. В репозиторий исходные архивы и частные диагностические данные не добавляются.

| Источник | Что обнаружено в исходниках | Роль |
| --- | --- | --- |
| Этот репозиторий, `0.19.0-dev` | `:app`, `:engine`, `:core:transport`, `:core:adb`, `:core:fastboot`, `:core:diagnostics`; Compose-экран USB и базовые проверки | Текущий APK и отправная точка CI |
| Архивный рефакторинг | `:usb:api/android`, `:protocol:adb/fastboot`, `:core:model/operation/artifact/diagnostics` и `:app`; десятки тестовых классов, UI, Actions | Основной кандидат на целевую архитектуру и перенос по слоям; **ещё не код этого APK** |
| Вложенный legacy | Старый `ru/forum/adbfastboottool`, XML UI, Quick Flash, ADB/Sideload, Fastboot, Mi Unlock, Welcome, `native_usbfs.cpp` | Продуктовые возможности, фирменный вид и референс быстрого USB; старые большие Activity/протоколы не копируем |
| Вложенный A2 | Эксперименты USB, ADB/Fastboot/Sideload, тесты и зафиксированная история решений | Источник проверок границ сессии, ошибок и аппаратных гипотез; не самостоятельная production-ветка |

Архивные документы описывают собственные Phase 0–4 как завершённые и Phase 5 как текущую работу. Эти статусы **нельзя переносить** в статус нынешнего репозитория. В самом архиве есть исходники из более поздних фаз; наличие файла не доказывает законченный сценарий или аппаратное прохождение его гейта.

## Сравнение решений, которые влияют на дальнейший код

| Тема | Этот репозиторий | Рефакторинг/legacy | Совместное решение |
| --- | --- | --- | --- |
| Имя и ID | `NekoFlash Pro`, `com.ncorror.nekoflash.pro` | Бренд `NekoFlash`, ID рефакторинга `io.github.ncorror.nekoflash`, у legacy старый `ru.forum.adbfastboottool` | Сохраняем бренд и текущий ID APK до отдельного решения о миграции/подписи; legacy package не используем |
| Android UI | Небольшой Compose-экран, тёмный/оранжевый | Развитый Compose UI и Welcome; legacy XML/иконка | Берём палитру/identity legacy, архитектуру современного UI развиваем отдельно |
| ADB | Авторизация и ограниченный фиксированный запрос | Рефакторинг имеет generic service, диспетчер потоков, shell/Sync/forwarding | Перенести по модулям с тестами, затем подключить к UI; не писать второй ADB engine |
| Fastboot | `getvar` и один ограниченный `download`/`flash` | Более полный engine/планы/`fetch` в архиве; широкий набор команд legacy | Один движок, честные peer-ответы и последовательное дополнение возможностей |
| Lock/размер | До DATA требуется известный лимит и размер раздела | В рефакторинге lock и значения `getvar` — advisories, если wire-операция корректна | Текущий запрет документирован как технический долг; изменить после проектирования и тестов, не в одной правке документа |
| Скоростной Fastboot | Нет USBFS/URB backend | Нативный путь есть в legacy и A2, в новом рефакторинге запланирован позже | Сначала базовый transfer и замеры, затем нативный backend со строгой отменой |
| Диагностика | ZIP событий, окружения и USB + TXT | Структурированные события/детерминированный ZIP в рефакторинге | Один формат с ограничением размеров, контекстом и обязательной проверкой обезличивания |
| Сборка/подпись | Gradle `9.5.0`, AGP `9.2.1`, Kotlin `2.4.20`, debug подпись раннера меняется | Gradle `9.5.0`, AGP `9.3.2`, Kotlin `2.4.10`; предусмотрен постоянный debug key через секрет CI | Конфигурации не смешиваем вслепую; обновление toolchain и постоянная подпись — отдельные проверяемые изменения |

## Как переносить

1. Выбрать одну возможность и её доказуемый контракт: USB session/ADB stream/Fastboot transaction, операция, artifact или UI.
2. Сравнить реализации и тесты; зафиксировать результат для этого репозитория. Не копировать целый legacy Activity или параллельный второй transport.
3. Установить API и владение ресурсом, затем подключить один рабочий путь и unit/fault tests.
4. Собрать APK в Actions. После этого провести ограниченный аппаратный сценарий на **одном тестовом устройстве с разблокированным загрузчиком**; hardware proof архивного проекта не заменяет эту проверку.
5. Обновить [статус](06_Roadmap.md) и [план тестов](02_Manual_Test_Plan.md).

Остались открытыми точный путь включения архивных модулей, решение о конечном applicationId, воспроизводимая debug подпись и способ проверки больших/sparse-образов. До закрытия этих пунктов архив не является заменой установленному приложению.
